# TorrentFlow system performance audit — 26 November 2026

## Baseline and method

Audited release source `f670fc0`, matching installed health `0.4.5+f670fc0d7cdf51120ce54f3b86d2f39bf5382846`. Installed health reported ready. Read-only: three sequential GET samples per route, aggregate completed GET timings in the current day log, inspect source and existing local test reports. No original DB/media read, no commands sent to downloads, no restart, no UI tabs changed. These are observational measurements under the owner's real workload, not controlled A/B profiling. Exact app/network/disk load and request overlap were not isolated. Logs include owner activity; no paths, release names or identifiers are copied here.

The three samples: `/api/client/torrents` 9,623 / 4,882 / 4,920 ms, response 1,117,217 uncompressed bytes; `/api/wanted` 5,151 / 5,057 / 5,321 ms, 23,966 bytes; `/api/notifications?limit=1` 4,853 / 8,456 / 8,210 ms, 340 bytes; `/api/health` 75 / 34 / 32 ms, 335 bytes. On Nov 26, log completed-GET samples yielded downloads median 9,426 ms, p95 20,557 ms (55); wanted 10,464 / 22,620 ms (47); notifications 6,924 / 16,925 ms (100). Selection bias: this is only completed requests logged while app was used; errors/uncompleted calls and concurrent load differ. The 5-second process sample was 0.17 CPU seconds, 3.4% of one core, ~786 MiB working set; this snapshot does not identify the bottleneck.

## Findings in priority order

### P0 — finishing repeatedly fails and can loop

Confirmed installed Nov 24: 3,137 `Completion verification failed` entries; Nov 25: 2,773; Nov 26 through 11:52: 2,001. The Nov 26 failures concentrate on two downloads and two file indexes, with `A completed or shared-piece file changed size`, and warnings `Could not publish download`. These are repeated attempts, not counts of distinct downloads. The earlier all-ready snapshot was true only at that time and did not establish the fix was durable.

Owning source: `backend/src/Engine/CompletionVerification.cs:101` rejects a shared-piece file whose stream length differs from torrent metadata; `backend/src/Targets/DownloadFiling.cs:147-156` converts a non-hash-mismatch failure to IOException; `:236-247` classifies IOException as temporary and schedules another attempt after 30 seconds. Thus a persistent mismatch retries repeatedly; evidence does not establish why the neighboring files have differing lengths, or whether retries themselves dominate request latency. Reproduce with generated mixed completed/incomplete pack data and targeted neighbor length/offset evidence. Verify file-index mapping, selected vs unselected neighbors and partial file allocation. Preserve hash and ownership guarantees; do not mark a file complete by ignoring the mismatch. Distinguish a durable evidence mismatch from genuinely transient access, bound retry/logging and give an actionable state only after its cause is established. Assert healthy siblings finish, no false Ready, pause/remove/retry/restart still work, and measure retries and disk bytes over several minutes.

### P0 — a live deletion has not finished after drain

At 23:28:30 local time the log recorded deletion drain completed in 28 ms. As of 23:32:06 (>3.5 minutes later), no corresponding `verified payload removal completed` log was present. `backend/src/Targets/TargetDownloadDeletion.cs:252-257` emits these phases, so the delay is after the drain log, but we cannot attribute it to hashing, disk, file locks, or database work without phase-level profiling. The app also reported 12 season-one entries `Removal did not finish` in an earlier read-only snapshot; no deletion was initiated by this audit. A 12.38 s POST finished nearby, but its action is not logged and must not be equated with the deletion. Current evidence does not show a faster real deletion.

Trace per-file verification and delete phase elapsed time plus bytes, queue/gate wait, cancellation and errors without logging paths; reproduce using disposable files with representative sizes, same disk type and shared-pack layouts. Compare 0.4.4/0.4.5 using identical copies and separate storage; assert no unowned files are deleted, and verify interrupted deletion recovery. The existing 58 MiB isolated result is not comparable to an unspecified real payload.

### P1 — notification badge executes the entire downloads read

Confirmed source: `backend/src/Api/Notifications/NotificationEndpoints.cs:18-29` reads all notifications and works and calls `downloads.ListAsync` then JSON-serializes the complete list merely to build a hash-to-poster map, even for `limit=1`. This directly explains unnecessary work but does not by itself quantify its share of the measured latency. `web/src/app/notifications/use-unread.tsx:6-9` polls that endpoint every 15 s. Desktop bell and mobile nav both mount (`web/src/app/layout.tsx:53,93`, `web/src/components/notifications/notification-feed.tsx:9`, `web/src/components/layout/mobile-nav.tsx:30`) even when CSS hides one, giving each hook independent queries. The notification page mounts an additional query. These facts are source-confirmed; browser network trace/dedup count is not yet measured.

Use a count-only authenticated endpoint/query for badges, filter notifications to the user in SQL, and fetch poster mappings only for the requested visible notification links. Share or deduplicate unread subscription across mounted shell consumers; preserve responsive badge, read/unread and notification updates. Benchmark `limit=1` and regular notification list at 100/1,000/10,000 notifications and 600+ downloads; compare SQL query count, bytes, median/p95 with simultaneous downloads polling. Verify unread count, poster on download-linked notifications, access control, focus/visibility and events; use real UI network trace.

### P1 — whole-library projection and scans per poll

`backend/src/Api/DownloadEndpoints.cs:203-217` calls `TargetPipeline.ReadAsync` and reads all links, works, names, episodes, seasons, releases, raw intents, bindings, media and roots. The loop at `:224` and row work at `:250-270` repeatedly scans arrays using Where/FirstOrDefault. `TargetPipelineRun.cs:16-28` loads all targets, downloads, attempts, scopes, raw intents and links to build each snapshot, including history that downloads projection does not use. `WantedRows` at `DownloadEndpoints.cs:556-575` scans all data and performs nested existence tests; `WantedAsync` at `:586` obtains a second full snapshot, then rereads works/names. `web/src/app/downloads/use-downloads.ts:60-62` polls downloads every 5 seconds; `web/src/components/wanted/wanted-actions.tsx:86` polls wanted every 3 seconds after the preceding request finishes. `useVisiblePoll` prevents overlapping requests within one hook; separate hooks and browser tabs remain independent.

The slow reads and 1.12 MB response are measured; repeated table loads and nested scans are verified source paths, but their separate runtime contribution, filesystem/SQLite contention and effect of concurrent finishing are unmeasured. Introduce purpose-specific projections with only needed rows/columns, indexed/grouped lookups built once per request, and avoid loading history where unneeded. Do not make Ready/file availability stale; preserve ordering, exact per-episode statuses, active download progress, access control, whole-season dialog and selection. Consider one shared snapshot per refresh or active-vs-inactive cadence, conditional on measured impact. Bench at 10/100/600/2,000 completed+active rows; collect request phase timings, SQL count/duration, allocation and payload bytes, sequential/concurrent p50/p95. Verify data parity against existing response for mixed raw/series/packs, missing files and active changes.

### P2 — React reprocesses full download response and renders all groups

`web/src/app/downloads/use-downloads.ts:31-50` reads and JSON-parses full response, replacing state after successful polls; `web/src/app/downloads/download-transfer-list.tsx:44-68` maps all visible groups and wanted-only rows without list virtualization. `use-downloads-page-view.ts` filters/groups/sorts the data. These are confirmed structural costs, not measured React commit/main-thread bottlenecks. Grouping series limits DOM rows relative to torrent count, so 600 torrents do not automatically mean 600 rendered rows.

Capture production browser Performance/React Profiler traces on 390/768/1280 viewports with generated representative 600+ rows and active updates: parse, group/sort, render/commit, long tasks, input latency and mounted node count. Optimize identity-preserving snapshot merging/memoization, grouping and pagination or virtualization only if measured. Preserve open dialog's full season independently of filters, keyboard focus, selection, scroll position, accessibility and accurate live progress. Compare saved trace metrics before/after.

## Scope, risks and limits

Source changes are proposals only; this is an audit. No flame graph, SQL timing breakdown, heap profile, production browser trace, filesystem latency probe, physical-device test, or real-world before/after deletion benchmark was performed. Installed log text identifies the size-check condition but not why files differ. The observed live deletion may still be running or fail, and should be checked again before any outcome claim. No performance issue should be considered fixed solely by this report. The Requests namespace also owns automation and notifications; removing user-facing Requests must not remove those shared services.
