## Blocking finding — deletion identity shortcut weakens changed-file protection

`backend/src/Library/DownloadFiling.cs:255-261` accepts persisted Windows identity, length and last-write time as sufficient to skip the old digest check. Same-object writes followed by restoring the last-write time leave all three values unchanged while bytes differ. File timestamps are mutable metadata, not a cryptographic content version; the code would delete the changed object even though the old behavior refused it. `LibraryPlacement.Inventory.cs:77` can also update recorded `MtimeUtc` during inventory without proving the old digest still matches, so an ordinary scan after a changed file can legitimize new metadata for this shortcut. `artifacts/system-latency/changed-delete.log` exercises changed bytes but not restored or refreshed timestamps. Retain the full guarded digest check unless a strong file-change token with appropriate guarantees is introduced and verified. Test edited same-length file with restored timestamp and inventory-refreshed timestamp; verify every file in a batch remains untouched on mismatch, while legacy and unchanged files work. Parent reports reverting shortcut and retaining the measured 1 MiB hashing buffer; re-review final diff/test before release.

## Sparse shared-piece completion

`Engine/CompletionVerification.cs:42-49,97-128`: the candidate still requires exact size of each selected completed file and verifies each touching piece against the torrent hash. A non-selected neighboring file needs only the bytes in the touching range, which permits legitimate sparse tails without dropping the hash. This is a sound narrow response to the observed changed-size failures. `sparse-red.log` reproduces old rejection; `sparse-green.log` verifies selected digest and shows corrupted and absent boundary bytes refused. `selective-full.log` records one actual generated selected target reaching Done with matching independent SHA-256. `final-formats.log` documents v1/padded/hybrid/v2 synthetic verifier coverage. No production files were inspected; the real mismatch's cause remains inferred, not established.

Caution: optional unguarded `VerifyFilesAsync` path opens the selected path at `:45-47` without the prior `RefusePayloadLinks` call applied to other files at `:104`; both current production callers provide held guards (Targets/DownloadFiling.cs:145; Targets/RawPublication.cs:103), so this is a latent interface regression rather than a demonstrated production exploit. Preserve no-link checks and consider removing unsupported unguarded use or add the check and test selected symlink/junction. Completion should continue to reject changed bytes, unavailable boundary, stale ownership, paused/removed intent and foreign finals.
