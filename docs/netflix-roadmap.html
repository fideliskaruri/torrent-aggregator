TorrentFlow: audit, and a plan to make it feel like Netflix

You have built a genuinely good engine with a search box bolted to the front. Netflix is the same engine with a catalog bolted to the front. This document covers what is there today, what is wrong with it, and the specific path from “search → send → wait” to “open the app → press play”.

Grouping, against real data A live breaking bad search — 96 results from real indexers — exposed three grouping defects the synthetic fixtures could not, because every crafted fixture name carries both a year and a quality token, so a cut always fires before the cleanup code is reached. Real listings routinely carry neither. The plain torrent Breaking Bad became a work called “Breaking”; El Camino rendered as two separate works because one print lost the word “Movie”; and a long bracket block left a heading reading El Camino - A Breaking Bad Movie (. A viewer dragging the native bar went nowhere. The native controls are suppressed in HLS mode and replaced by one transport bar that speaks only in film time: play/pause, position, seek, mute, full screen. The icon follows the media events, not the click, so a refused autoplay can't leave a pause icon over a stopped video. This also made the test honest — the harness previously called video.play() in JS because native controls live in shadow DOM and cannot be clicked; it now clicks the real button. Verified end to end against a live swarm: 19/19 in real Edge.
The home page, finally looked at Nothing in the repo ever seeded the local user, so every screenshot ever taken of / was of the empty board — the product's actual home page had never once been rendered with data. The first time it was, two defects were sitting in plain sight that had survived the whole suite, a code review and eighteen screenshots: every poster-less card printed its title twice (once inside the artwork box, once in the caption eight pixels below), and the downloads heading announced as “Active downloads2”. The no-artwork tile is now a mark only — tint, hairline, ghosted initial — which is the rule the hero variant already followed and the card had simply missed. The heading needed an sr-only comma, not a space: CSS Flexbox drops whitespace-only children, so the usual {" "} fix is silently ineffective in a flex row. Both are locked down by a new npm run test:browse, which seeds a library, photographs the board, asserts against it and removes exactly the rows it added. The duplicate-title assertion was proven by re-introducing the bug: it caught all nine cards.
The library told you it was empty when it was merely unreachable The one page left that still hand-rolled its own fetching. /watchlist ran the same request twice — a load callback and a near-identical mount effect — and rendered its error banner and its empty state as two independent branches. So a failed load showed the error and, directly underneath, “No items yet — Search a show, Add to library”: the app instructing you to go and rebuild a library you already have. It looked correct at a glance, which is precisely why it survived. Both copies replaced by useApiQuery, and the branches collapsed into one exclusive chain ending in TfErrorState with a working retry. Added to npm run test:errors (now 33/33) and proven not to be vacuous by running the new case against the pre-fix build first, where it failed. Because the rows are server-owned but locally editable they sync into state during render — a sync that could break silently and just look empty — so a new npm run test:watchlist seeds the library, renders it and works a filter to prove the state is live rather than a frozen snapshot.

Known gaps — deliberately not hidden

Now exercised end to end: a real torrent streams through the playback ladder — a local BitTorrent swarm (2 peers, no public tracker is ever contacted) feeds the byte-range route, ffmpeg reads it, and the produced fMP4 is re-probed to confirm 6 channels in → 6 channels out on both the remux and the DTS→E-AC-3 rungs. The real player was then driven in real Edge: click to play, pause, seek, and an audio-track switch that returns to 5.1 without a silent downmix.

Still not exercised: the hardware AMF encode path (the encoders are present; nothing selects them), the MediaProbe DB cache, and Web Audio channel readback — we prove 6 channels reach the decoder, not that the decoder emits 6. Degraded here but not in general: TMDB_API_KEY is empty on this machine, so catalog metadata — posters, proper titles — is thinner than it will be for you with a key set. Everything is uncommitted, sitting in the working tree, so you can read the whole diff before any of it becomes history.

1. What you built

TorrentFlow is a single-process replacement for the *arr stack. One user, no sign-in, bound to 127.0.0.1. The entire product is one pipeline, and every module is a stage of it.

Aggregate

Six indexers behind one interface — Nyaa, apibay, Torrents-CSV, YTS, EZTV, optional 1337x. Adapter failure is isolated; a dead source degrades the result set, never the request.

Rank

A Sonarr-derived comparator in quality.ts. Ordering is target-relative, not “bigger is better”. Nothing is ever rejected for resolution.

Fetch

In-process WebTorrent with durable state in EngineTorrent. Survives restarts. Optional qBittorrent / Transmission for people who want them.

File

Content-layout policy strips release-name wrapper folders so files land in TV/Show/Season 03, with a repair pass for what already landed wrong.

Automate

A per-show hunt cursor, a run lock, miss backoff, and a scheduler. It knows which episode each monitored show is waiting for.

Play

HTTP 206 byte-range streaming straight out of the live swarm via file.stream(). Built-in engine only — there is no qBittorrent equivalent.

The thing worth protecting. docs/handover.md and the commit messages (“stop the pollers lying”, “stop unseeded episodes from silently skipping a season”) are unusually disciplined. The invariants are real and they were each paid for with a bug. Any refactor below must carry them forward, not rediscover them.

5. The Netflix thesis

Netflix's experience rests on three guarantees. You have none of them, and only one is actually hard.

Netflix guaranteeWhy it holdsTorrentFlow todayDifficulty
Instant playbackBytes are already on a CDN edgeBytes are addressable but absent. Seconds-to-minutes of latency.Solvable — §6, §7
A catalog to browseA fixed licensed library, merchandised into railsNo catalog. An empty search box demanding you already know what you want.Easy — you already call TMDB/AniList
ContinuityServer-side progress, auto-advance, next-upNone. The player forgets you the moment you close the tab.Easy — small schema add
It just playsEvery asset transcoded to browser-native H.264/AACWhatever the release group used. Often HEVC/AC3 in MKV.Hard — §8

The trap to avoid. The naive version of this project skins the search results as posters and calls it Netflix. That produces an interface that lies: everything looks equally playable, you press play, and nothing happens for ninety seconds. The whole design problem is making absence legible without making it depressing.

6. The availability model — the one idea that matters

Stop treating “downloaded” as a binary. Model every playable thing as one of four states, render that state everywhere, and let it drive which button you show. This is the primitive the entire redesign hangs off.

StateMeansDerived from (code you already have)Button
Ready On disk, complete. Plays instantly, seeks anywhere. EngineTorrent.progress === 1 Play
Warm In the swarm with enough throughput to sustain playback. Plays now; seeking ahead may stall. live torrent + downloadSpeed > bitrate
prefetchBuiltinFileEdges done		 Play + buffer indicator
Fetchable A viable release exists. One click and ~30–90s from Warm. rankResults + isViable() in runner.ts:380-423 Get it → countdown
Unavailable Nothing viable. Say so plainly and offer to watch for it. empty pool, or all below viability gate Notify me

Why this is cheap for you specifically

  • isViable() already encodes “can this swarm finish”, complete with the 6-hour seederWaitSince escape hatch. That is the Fetchable/Unavailable boundary — it just isn't exposed to the UI.
  • The stream route already answers 425 while metadata is pending. That is literally the Cold→Warm transition, already wired.
  • EngineTorrent already persists progress and status across restarts.

Design rule: never show a Play button that will not play. Show Get it, show the countdown, and let the state chip do the honest work. Netflix earns trust by never disappointing a click; you earn it the same way, by promising less per click.

7. Pre-warming — how you actually beat the latency

This is the highest-value idea in the document, and you are already 80% of the way there without knowing it.

WatchListItem carries cursorSeason / cursorEpisode: the exact episode each monitored show is waiting for. That field exists so automation can hunt. But it is also a prediction of what the user will press play on next. 

// today
user finishes S03E04  →  opens app  →  searches  →  sends  →  waits 90s  →  plays

// with pre-warm
user starts  S03E04  →  engine quietly fetches S03E05 in the background
user finishes S03E04  →  "Next episode" is already Ready  →  plays instantly

The pre-warm triggers, in priority order

  1. Next episode of what is playing now. Fire at ~15% watched. Highest hit rate by a mile.
  2. Next episode for every show in Continue Watching. Bounded by a disk budget.
  3. Metadata-only warm for the first item of each Home rail — fetch the torrent metadata (not the content) so the Get→Warm transition is instant rather than a DHT round-trip.

Budget it against disk-space.ts, which already enforces a storage cap and free-space floor on every send. Add an LRU eviction policy for pre-warmed content that was never watched — pre-warming must never evict something the user explicitly asked for.

8. The codec wall — the one genuinely hard problem

Be honest about this before building the UI around it. A browser <video> element plays H.264+AAC in MP4 and little else. A large share of torrent releases are HEVC/x265 video or AC3/DTS audio in an MKV container. Those will show a black screen, or video with no sound, no matter how good the streaming route is.

OptionWhat it meansCostVerdict
A. Probe & direct-play Read the container/codec from metadata, mark playable releases, and prefer them in ranking when the user's intent is “watch now”. Hand everything else to VLC. Low. A codec term parser plus a ranking tiebreak. Do this first
B. Remux on the fly ffmpeg copies H.264 video + AAC audio out of MKV into fMP4. No re-encode. Medium. Bundle ffmpeg; near-zero CPU. Phase 3
C. Transcode Full HEVC→H.264 re-encode, HLS segments. High. Real CPU/GPU, a job queue, a cache. Only if you must

Recommendation: A now, B in phase 3, C never unless you personally hit it often. Crucially, option A is a ranking change, and your ranking layer is the best-tested part of the codebase. Add a directPlayable signal to quality.ts as a tiebreak — never as a filter, per your own standing invariant that nothing is rejected for its encoding.

10. Schema changes required

Small. Three new models and a handful of fields — nothing that forces a migration of existing data.

Codec incompatibility makes “just press play” a lie for a chunk of contentShip §8 option A in Phase 2, before the browse UI promises anything. Prefer direct-playable releases; be explicit when handing off to VLC.
Pre-warm fills the disk with things never watchedEngineTorrent.origin + LRU eviction of prewarm-only + hard budget from disk-space.ts. Never evict user-requested content.
Rails make the app feel slow if each tile resolves a torrentNever resolve on render. Availability is a cache refreshed in the background; tiles read it, they don't compute it.

TMDB rate limits under a browse-heavy UICatalogEntry is the cache; rails refresh on a timer, not per-request. You already use next: { revalidate }.

Explicit non-goals

  • Multiple profiles. Single-user is a stated product decision; the userId seam already exists if that ever changes.
  • A hand-rolled recommender. Your handover doc is right — a bespoke recommender over a five-row library is strictly worse than the catalogs' own endpoints.
  • Full transcoding. Option C in §8 until proven necessary.

13. If you only do one thing

Phase 0's grabPipeline() extraction, then Phase 1's PlaybackProgress.
