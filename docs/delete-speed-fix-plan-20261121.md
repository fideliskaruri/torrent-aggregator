## 1. What the repair must improve

The installed torrent command took **180.534 seconds** from 01:02:39.493 to 01:05:40.027 Nairobi. The log lacks the request body, stage durations and per-file results. The 27.9 GB read counter covers the whole process since startup. Four costs are directly visible in the released source: a command per episode, repeated stop/recovery of the same pack, repeated SHA-256 reads of the same filed media and engine state saves covering unrelated managers. Measure their contribution in isolation. [Diagnosis](delete-speed-diagnosis-20261121.md)

The first target is an ordinary **Delete with files** command for unfinished downloads using release defaults. For a shared pack, resolve the submitted episodes into one file-index union, drain the affected manager once, remove exactly the authorized entries and recover surviving work once when required. A finished file with a saved digest still costs one content read. Missing files need no payload read. Both release web code and its command DTO omit the current-file checkbox seen in the screenshot. Its origin is unverified. The fix requires neither that checkbox nor a database of trusted timestamps.

The coordinator has prepared `audit-runtime/deletion-performance` on `fix/deletion-performance` at `46b60c8`. Use that worktree for implementation and isolated tests. Its product sources match `f174b64`; the planning document lives in the adjacent `anime-english-fix` checkout.

## 3. Resolve exactly what the owner selected

1. In `Api/DownloadEndpoints.cs`, keep owner authorization, existing selector/count limits, and pause/resume/keep-files routes. Route tracked **delete-with-files** to one bulk method on `TargetPipeline`. Validate the complete selector list before mutation. Normalize the hash only, compare target suffixes ordinally, preserve existing hash-only idempotency where applicable, and reject stale target/hash combinations. Use scoped DB projections in lieu of `targets.ReadAsync`, which also requests live engine state. Explicitly bind the optional mixed-client field `confirmCurrentFiles`: missing/false uses the normal path, true returns a protocol/version error before changes. No physical override in this release.
2. In `Targets/TargetDownloadDeletion.cs`, resolve authorized targets, links, bindings, file roles, media and root into immutable per-download selections. A request processes one hash at a time. Overlapping whole/episode selectors deduplicate. Explicit whole-hash requests honor the existing earlier **Remove, keep files** exclusion. Selecting all current targets grants only their captured entries. Collapse to full cleanup only if every owned live binding is accounted for and no protected/orphan binding would be lost. Keep a target with another present copy owned. Preserve replacement associations and Jellyfin deletion jobs for the correct media IDs. Account for already-gone, selected targets with no files without inventing a path.
3. Capture entries from explicit bindings and associated media: the actual engine partial, filed final, inventoried owned media path, and exact private unwanted index paths where full ownership permits. Never infer another file from a suffix or enumerate an unknown descendant for deletion. Prune only anchored empty directories. An unknown child survives and keeps its directory. Include collisions against kept and unselected bindings, media and outstanding path claims across downloads. Recheck ownership/version immediately before destructive work. Discovery of new members cannot enlarge a submitted selection.
4. Keep caller-specific intent. Library's `DeleteLibraryAsync` checks Jellyfin playing and playback-unknown before the tracked executor. Its explicit playback override retains only that meaning. `TargetRecovery.FindAnotherCoreAsync` requeues its explicitly captured targets only following a successful removal and a fresh version check; an intervening user delete wins. Keep raw `RawDownloads.RemoveAsync` and Library's unbound/import-only path with their existing resolvers. Exercise regressions at these boundaries, and exclude their independent performance from tracked-path claims. Do not funnel raw paths, unbound media or keep-files through the tracked verifier.

## 4. Reserve, drain and fence stale work

**One additive database column.** Add nullable versioned JSON `PendingFileDeletion` on `DownloadRow` through `Domain/Records.cs`, `Store/TorrentFlowDbContext.cs` and an EF migration/snapshot. Existing rows default to null. An interrupted physical delete must be distinguishable from an earlier keep-files choice; `Removed` and `Stopped` already serve other purposes. Existing per-file operation rows control filing, and lack this captured multi-file selection and sibling intent. Keep pending data only for unresolved work. Use existing download version compare-and-swap. The payload holds operation ID, prior sibling intent, root ID/native identity, captured target/link/binding/media IDs and exact root-relative entries, their evidence and outcome. Store only selected entries and references needed to reconcile. Stream processing per torrent and apply existing request/torrent metadata validation to bound size. Avoid full-library snapshots and per-success history.

Generate the EF migration target model/designer and update the static model snapshot together. Exercise both published-release and existing audit-build upgrade fixtures against disposable databases. Assert the new nullable field, preserved data/associations and no pending model changes. A partial schema match cannot establish that a migration completed.

**Lock order and handoff.**

| Owner | Ordering and invariant |
|---|---|
| Targets | Under the short state/DB transaction, compare captured rows, reserve the download and fence selected target leases/retries. Registration of affected filing/admission work must atomically see either the reservation or its pre-existing task. Release state and transfer gates before waiting for that task. A registered filer may settle or yield; re-read versions, media and paths afterward and stop on a changed selection. `TargetTransfers.StartFiling/FileDownloadAsync` finishes through `Targets/DownloadFiling.cs`, which itself needs `stateGate`. |
| Work on the same download | Serialize competing destructive operations by durable download ID or canonical hash; never hold two per-hash owners. Existing pending operation means reconcile/return its outcome or accept a fresh explicit retry of its captured remainder. Do not admit a new selection over it. Reclaim idle mutex entries. Release all global gates before awaiting the per-hash owner. |
| Engine | A short engine-map lock records the manager identity/epoch, marks it closing and signals existing integrity/admission work. Release the lock before awaiting the existing hash lease or outstanding task. Once the hash lease is acquired, briefly revalidate the same entry under the map lock. Stop, drain and close outside the map lock while the hash remains reserved. Finish map changes under the short lock. Snapshot/queue/tick/hash/admission callbacks honor the closing generation. They must not re-enable it or hold the map lock waiting for it. No Target state or transfer gate spans these awaits. |
| Pending writers/restart | Gate `TargetTransfers` admission/join/tick/recover, scope leases in `TargetPipelineRun`, user actions/retry/source replacement, filing register/commit, engine capture/rebind and storage/file operations touching the same entries. Revalidate the token/version at side-effect time. Exclude affected work from queue admission and replay. Target-scoped invalidation allows unaffected members of an existing grouped search to continue. |

For the actual barrier, install a delegating `IPieceWriter` through existing `Factories` in `MonoTorrentEngine.InitializeAsync`. Track in-flight operations per manager file object, including writes, reads, moves, flushes and closes. Existing candidate `DrainingPieceWriter` forwards writes without tracking them. First stop new source/queue work and quiesce the manager. Allow the engine's final cache flush to drain, then seal that manager's file generation against any new payload I/O, await outstanding I/O and close handles. Permit required close operations while sealing. A stale generation can never open/write again. Use explicit failpoints immediately before/after flush, close and a delayed write. A missing manager with no registered claim/writer/operation needs no artificial drain. `DownloadRuntime.StopDownloadAsync` currently suppresses a flush exception and `StopAndReleaseFilesAsync` returns success anyway. Carry distinct detached, writes-drained and failure facts to Targets. Any uncertain flush/close leaves files intact and retryable. No file hashing or disposition until the barrier passes.

## 5. Verify and remove each authorized entry

The first implementation optimizes the reported Windows tracked-download path. Preserve existing platform routes outside that adapter, exercise a portable smoke check where available, and label their coverage separately. Never silently substitute a path-based unlink inside the verified adapter. A Windows volume lacking the required operations returns a capability error before unlink. A production claim for another platform needs its own native race tests.

* **Engine partial.** Authority is the exact active/unfiled binding to the stored engine/partial path, under the assigned root, with no competing claim or media ownership. Pin the root and record the entry identity when taking the inventory using a metadata handle compatible with the writer. Match it again after quiescence. Do not hash continually changing bytes. If the file was absent initially but is created by a final in-flight engine write, accept only creation tied to this captured writer generation and index; otherwise preserve the new occupant. A final/imported path or ambiguous former partial cannot gain partial-file authority by name.
* **Filed media.** Require the historical SHA-256 when release semantics require it. Stream it once through the same retained file object used for disposition. Match every referencing media/binding digest for this object. Conflicting expectations fail safely. A missing digest for a final file that needs historical proof returns a verification error. Equal size/creation/write/change times or a matching file ID cannot establish unchanged contents. No identity-column migration, permission bypass or startup backfill.
* **Windows entry ownership.** Anchor the configured root and populated parent chain with no-follow directory opens, reject reparse traversal, verify configured volume and native root identity, and deny directory rename/delete sharing while descending. Open the leaf with read and delete rights, excluding write/delete sharing, verify its identity and reparse attributes, hash if required, and set the verified handle's disposition. Bound handles to one object group plus ancestors. For selected hard-link aliases, retain a read-only pin excluding writes but sharing deletion while opening each authorized entry handle sequentially. Explicitly distinguish an unselected separate hard link (preserve its entry) from an unselected claim on the same directory entry (refuse).
* **Completion.** Close the disposition handle and required pins, then inspect through the still-anchored parent. Confirmed absent on the correct online volume permits metadata retirement. A replacement survives. Delete-pending, inaccessible, offline, changed root, or unknown evidence returns an unresolved result and keeps inventory available. An open reader can delay Windows removal; use a bounded observation and never wait forever. Only remove empty inventoried directories. An outstanding link or handle prevents a claim about freed space.

Windows documents both modifiable metadata timestamps and delayed file disposition. [File basic information](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_basic_information) · [File disposition information](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information)

## 6. Commit facts and restore only surviving work

1. Persist the complete captured intent and original binding facts **before any unlink**. Make the reservation and cancellation visible atomically. Wait for filing, validate/update recorded entry identities under the same reservation, then perform the barrier. The manifest establishes exactly which entries could have been touched, so no DB transaction or progress write is needed between each filesystem call. For large groups checkpoint completed facts in small transactions. Never hold a SQLite transaction across physical I/O.
2. After a definite removal/absence, stage that entry's outcome. Apply factual outcomes to bindings/media, exact links, target ownership/alternate copies and existing Jellyfin cleanup in a single scoped DB transaction per commit. Refactor `Store/LibraryRemovalRepository.cs`/download repository transactional helpers for reuse instead of nesting their current separate transactions. Check full captured binding values (bindings have no version column), media/download versions and path claims. A failed subtitle can remain retryable after the video succeeded. A target with any unresolved entry stays visible on hold; an absent file's successful associations stay removed. Keep confirmed and unresolved IDs in the response and project pending rows in the existing Downloads read independently of active target state.
3. Full cleanup removes registrations/claims, retires the old resume evidence and transitionally retains the DB fence until stale state cannot restore that download. Partial cleanup retires deleted indices via `DownloadFiling.RetireBindings`, preserving the complete index-to-path map required by `BindAsync`. Failed selected entries remain held and never write to their old public paths. Where a surviving selected file shares a torrent piece, direct required boundary data to its exact private unwanted index. Keep this distinct from recreating public files. If no collision-free safe mapping exists, pause remaining work with a reason. Preserve the newest legitimate sibling run/paused intent. Rebind/recover once for remaining unfinished work. Honor integrity checks on changed mappings, failed flush or unclean shutdown. Inspect `StartAsync` results inside `RecoverAsync` and verify resulting manager identity, priorities, selected paths and queue state. Recovery failure affects siblings and has its own result; never report deleted files as still present.
4. Avoid repeated global saves from stop, delete and the outer command. Collect affected mutations and issue at most one required whole-engine checkpoint per batch, independent of the number of episodes. Preserve per-hash resume evidence as needed. The durable database decides recovery. Both `Api/EngineModule.cs` startup and `MonoTorrentEngine.InitializeAsync` dev-artifact restore must honor pending fences **before load/bind/hash/start**, including stale cached state after a full removal. When a cache cannot be filtered safely, discard that disposable cache and replay eligible durable downloads. `TargetPipelineRun.RecoverAsync`, `TargetTransfers.RecoverAsync/TickAsync` and the explicit recovery endpoint observe the same fence.
5. On disconnect/cancellation, stop initiating further unlinks. Once any disposition has been attempted, reconcile known outcomes under a bounded host-owned token independent from the HTTP request. After a crash, re-probe the exact recorded entries on the original online root, finalize confirmed absence, and leave present/replaced/unknown entries visibly on hold. Never resume destructive I/O automatically. Explicit retry resolves only the recorded remainder against current ownership and evidence. A changed object keeps its protection. Resolve the row and clear its field once DB facts and sibling recovery agree; leave a scoped recovery reason if sibling activation fails.

## 7. Command completion and acceptance

Return existing HTTP 200 and `{ok:true}` only for fully applied deletion. Use a non-success response with `ok:false`, a concise message, resolved and unresolved transfer IDs and separately identified sibling recovery failure for partially applied commands. Validation errors have zero side effects. The released UI in `use-download-management-actions.ts` already clears the submitting flag in finally. Update `use-download-row-actions.ts` to refresh authoritative rows on all outcomes, clear just successes, select retryable failures and distinguish transport-unknown from server failure. Stop duplicate submits and stale poll overwrites. Keep normal success in Downloads. Verify a missing/malformed reply, timeout, stale 200, partial result and pending list refresh in the isolated UI. Follow repository flow-first gates before UI edits.
