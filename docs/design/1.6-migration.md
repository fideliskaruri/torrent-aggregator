## Tool contract and order

`convert --source-db <copy> --source-data <copy> --destination <new-data>
--path-map <reviewed-json> --mode rehearsal|live --plan|--apply --copy-payload|--move-payload`

Source database is **always read-only**, never attach for update or run old EF migrations.
Use SQLite backup API from a read-only connection to make a consistent destination
snapshot including WAL (ordinary copying .db without WAL is not sufficient).
Schema fingerprint (`sqlite_master` + PRAGMA table_info), old row counts and SHA-256
backup/artifact digests are recorded in Setting.migration in the **destination only**.
Reject unknown required columns/schema or backup failures; never silently omit data.
Offline converter acquires an exclusive destination conversion lease; no new API serving
until final integrity/foreign-key checks pass. Source read-only can coexist with a running
old server for rehearsal, but live cutover requires owner stop and final backup first.

1. Inspect/plan: report paths, rows, malformed JSON, duplicate identities, unresolved work
   mapping and physical files. No modifications, no provider/network calls.
2. Create separate new Store schema; ensure local owner; migrate Work/links/names; create
   stable Season/Episode from confirmed old numbering, never fabricate provider facts.
3. Settings/secrets/root mappings+volume identity+existing WorkFolder pins; watch/follow/
   preferences/users/requests/ScopeIntent/RawIntent/blocks/history. UpgradeEvidence starts
   empty (old unverified best-release hints do not become healthy evidence).
4. Release/engine metadata/file manifests, then Targets and associations, then inventory.
5. Plan per-file `.staging` moves and pending old relocation/deletion recovery. Apply only
   to **explicitly mapped copied payloads** in rehearsal. Rehearsal NEVER reads/mutates
   legacy absolute `D:\Torrents`/local-appdata paths. Live requires an owner-reviewed
   **identity path map for all real roots**, including unchanged `D:\Torrents` paths:
   verify existing files read-only, do not mark Missing simply because no copied path exists.
   No legacy application-data mutation in either mode; live payload movement only under
   separately explicit approved operation, never implicit conversion/tidy.
6. Hash check/resume reconcile, owned reconciliation, request settlements, notifications.
7. Check counts/columns; publish new data path atomically with scheduler **paused**.
   New server completes the first full identity-valid root scan before any
   acquisition/Follow/rule/speculative payload admission. Auto-adopt only exact-path
   Confident matches against known catalog/file evidence; ambiguous or unmatched
   media remains available for owner review, never guessed ownership.
   During this gate queued API intent remains visible; no start based on converted failed
   targets alone. Root identity failure keeps scheduler paused and asks owner.

Deterministic destination IDs use preserved source IDs, or UUID v5 from
`sourceFingerprint/table/primary-key/subitem`. Conversion phases/upsert keys live in
Setting.migration; FileOperations record each physical effect. Re-run resumes identical
effects without duplicate Targets, Requests, files or notifications. Dry run emits report
files only inside the chosen destination/project, never a temp directory.

## Staging relocation and rollback

For each mapped `.staging\<hash>` file: load verified torrent metadata; inspect all
filenames for danger; map indices to final layout/selected episodes; record operation
and destination claim. Copy to final `.partial` (rehearsal default), compute SHA-256 both
files for byte identity; torrent piece-hash verify completed ranges for resume correctness
(SHA-256 equality of two corrupt copies is not proof of valid torrent). Full valid media
then passes content sniff, renames in place and records MediaFile. Incomplete valid pieces
stay partial with rechecked bitfield; unknown metadata waits, not Ready.
Only after verified destination+durable inventory commit may `--move-payload` delete its
explicitly approved staging source. Same-volume rename still records precomputed digest
and verifies after rename; idempotent restart handles either side without overwriting.
Existing final files kept untouched if already verified; conflicts need review.

Rollback keeps old server binary, DB+WAL-consistent backup, seven side-file originals,
engine artifacts and folder manifests. During rehearsal **copy only**. During live
move record inverse mapping/digests in destination operations and retain backup payload
copies for a week. To rollback: stop new server with owner; export any post-cutover new
files/intent separately (do not write new schema into old DB); restore moved originals
from verified backup/inverse map without overwriting post-cutover files; start old server
against untouched old DB/config. New server never shares old DB.
**Rollback payload fence (OPS-656):** before old-server startup disable its layout tidy,
promotion and same-size replacement paths. Verify the disable switch/config actually
prevents these jobs; if unavailable, quarantine post-cutover files out of shared folders
using the exact recorded path/digest map before old start. Do not let old cleanup overwrite
new-server publications. Preserve/export quarantine inventory for later explicit recovery,
never silently discard new files. Rehearsal proves this fence on copies before live cutover.
No old server cleanup until owner approves after a week.

## 7.1 rehearsal implementation and edges (OPS-772, 2026-10-03)

The implemented offline tool is `backend\tools\Convert`:

```powershell
dotnet TorrentFlow.Convert.dll --from <copied-old-directory> --to <new-directory> --path-map <json>
```

The broader switches above describe the cutover design, not implemented CLI options.
This tool currently supports rehearsal only. It takes a SQLite backup including WAL,
retains source columns and side files in `legacy-backup`, then publishes a completion
marker after integrity and foreign-key checks. A completed rerun is a no-op. An
incomplete destination without its marker is rejected, not incrementally resumed.
